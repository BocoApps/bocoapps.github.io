What is My Database Pro?

My Database Pro is an all-in-one mobile tool for creating, browsing and managing databases directly on your phone — with no server required to get started. It combines a full local SQLite database manager, a remote MySQL client, a photo-capable record editor, an SQL console, a multi-tab code editor with a real built-in PHP interpreter, a web browser view, an SSH terminal, and an AI assistant that can write and run SQL for you in plain language — all in a single app.

The AI assistant runs on an account of your own. The app carries no API key and sells no access to a model: you sign up with a provider, create a key there and paste it in — or point the app at a model running on your own machine, which costs nothing and never leaves your network. Section 14 says how. Everything else in this list works with no account of any kind.

A database created in the app can also be turned into a fully working website with one tap: the app generates a ready-to-use PHP page that displays your data as searchable, image-rich cards on any web server you own, complete with its own AI search box.

The app is translated into 50 languages, and the language can be chosen independently of the phone's own.

This page covers every screen and feature. The same page is inside the app: Setup › How to opens it, with no connection needed.

1. The Tool Row

Every screen in the app carries the same row of buttons: Home and the five tools. The buttons never move, so wherever you are, the one you want is under the same thumb.

ButtonGoes to
HomeStraight out to the database list, however deep you are.
SQL QueryThe SQL console, on whichever database you last used it.
AI ChatThe assistant.
EditorThe multi-tab code editor.
Web ViewThe in-app browser, on the page you last read.
TerminalThe SSH terminal, reconnecting to the last connection.

Two things worth knowing

  • The row moves. Hold a finger on it and drag, the same gesture that reorders the database list, and it docks at the top or at the bottom of the screen — whichever end you let go on. Where you put it is remembered, and every screen follows.
  • It returns rather than restacks. Pressing Editor while an editor is already open drops back onto that live screen with all its tabs and unsaved text intact, instead of opening a second one on top. The same is true of every tool. That is also why the trip is instant.

The button for the screen you are on is drawn with a filled background — since the row is identical everywhere, that patch of colour is what tells you where you are.

Setup is deliberately not on the row. It is not a tool, and it is wanted about as often as a new database is, so it lives in the database list's own title bar next to the buttons that add one. It is a screen of its own, so the tool row stays on it.

2. Main Screen — Your Databases

The app's home screen. It lists every database you have: local SQLite databases (shown with a database icon) and remote MySQL connections (shown with a cloud icon).

Title bar

  • + Creates a new local SQLite database, or adds a MySQL connection.
  • Import Imports from a CSV file, a ZIP archive (database plus its images), or a plain .db SQLite file.
  • Setup The app-wide settings screen — see section 15.

Managing the list

  • Long-press and drag a database to reorder the list. That order is used everywhere else too, including the database picker inside SQL Query.
  • The three-dot menu on each database offers: rename, duplicate, delete, and a password. A MySQL connection has Edit Connection in place of rename. Which table opens automatically at app start is set on the table itself: Table Options → Set as Default.
  • The password means two different things, and the menu says which. On a local database it is SQLCipher: the file itself is encrypted and without the password there is nothing to read. On a MySQL connection it is the connection lock — one key over the screens that show your logins, which is section 16 — and the menu says Lock with password and Remove lock there. Both draw the same padlock on the row.
  • A MySQL connection can have a second password, over its form alone. At the bottom of Edit Connection, under the heading of the same name: Add Password. Once it is set, Edit Connection and Delete ask for that password and no longer for the connection's own — so you can lend somebody the database with the connection's password, and they can open it but cannot read the host, the user or the password it logs in with.

Sort by — which column a table is listed by

On a table's own three-dot menu, Table Options, on the screen you reach by opening a database. It sets which column each table of this database is listed by in the Records screen, and in which direction.

  • It is per table, not per database. Your tables have different columns, so one name for the whole database would work on some tables and quietly do nothing on the rest. Each table's menu sets that table's order and leaves the others as they are.
  • Pick a date column and it suggests newest first. That is almost always what a date is wanted for — otherwise today's edit lands at the bottom of a long list and it looks as though nothing happened. It is only a suggestion: change the direction and your choice sticks.
  • The published PHP pages follow it too — see section 9.
  • The setting lives on this phone, next to the column visibility, and it travels in a backup. An ORDER BY you type into the Records screen's <> search still wins — it is the more specific instruction.

Display — how this database's records are drawn

On the three-dot menu at the top right of the screen with the tables, with Export Database and Import — not in Table Options, because it is one setting for every table of the database. Three settings, each about this database only.

  • Show all posts on open — whether opening a table fills the list straight away, or waits for you to search. On a table of a few hundred records with photos, waiting is the faster screen.
  • Show images — whether the strip of thumbnails is drawn at all. Off is how one database shows plain rows while another still shows its pictures.
  • Thumbnails — how big they are, 50% to 300%.
These used to be in Setup, for every database at once. That is why they moved: turning the pictures off for a table of printers took them off Chinook too. A database you have never opened this screen for keeps whatever those old app-wide settings were, so nothing changes by itself. Like Sort by, the choice lives on this phone, it travels in a backup, and it follows the database through a rename.
A fresh install arrives with two sample databases already unpacked — Chinook (the classic music-store sample, good for practising SQL) and Animals (a small picture database that shows what image support looks like).

3. Tables Screen

Tapping a database opens its list of tables. From here you can:

  • Create a new table with + in the title bar; rename, duplicate, sort or delete one from its own three-dot menu, Table Options.
  • Reorder tables by long-press and drag.
  • Open any table to view and manage its records.
  • The three-dot menu at the top right has Export Database, Import (a CSV into this database) and Display.
  • The <> on the tool row opens SQL Query on the database you are in. The database's name on the line under the title bar is a menu: tapping it switches to another database without going back.
If a database is password-protected, you will be asked for the password before its tables are shown.

4. Records (Posts) Screen

Opening a table shows its records. Depending on a setting, records are shown either 100 at a time with paging, or all at once.

Working with records

  • Add, edit and delete records. Each record is made of text fields (the table's columns) and can also carry one or more attached photos.
  • Photos can be added from the gallery or straight from the camera. EXIF rotation is corrected automatically, so a photo taken sideways is stored the right way up, and a thumbnail is generated for the list.
  • Several photos can be picked at once. Thumbnails appear inline; tapping one opens a full-screen viewer with pinch-zoom and swipe between photos.
  • Hold a photo and move your finger to drag it into a different position.
  • Hold a photo and let go without moving to select it — it darkens and gets a red tick. While photos are selected, a tap selects or unselects another instead of opening it, so you can pick one, several or all of them. The bar under the photos shows how many are selected: the red bin on the left deletes them all at once, after asking once, and the ✕ on the right cancels. The camera button is hidden while you are selecting, so the bin is never beside it. Selecting works on one record at a time, and moving a photo clears the selection.
  • Images live in a folder beside the database and are referenced from an image_paths column, so they travel with a ZIP export.
  • Changing the photos updates the record's date. Adding, removing or reordering one changes a file rather than a column, so the database would otherwise never notice — and a record sorted newest-first has to move when its pictures change. If the table has an updated_at column, the app stamps it.

What a card shows

A card draws the columns you chose, in the order you dragged them into. That choice is on the Columns view — the same screen that adds and renames columns — where every row carries an eye: press it and that column is off the card, press it again and it is back.

  • Camera and delete is the last row of that list, and it is the two buttons the card draws in its own corners: the ✕ that deletes the record and the camera that adds a picture to it. On a table that is read rather than edited they are two buttons in the way of every record — one eye puts both down. Press it again when you want them back, because the corners are where those two live.
  • It is kept per table on this phone, beside the other things about the record list, and it follows a table rename, a duplicate and a backup.

What you can do with a picture

Tap a thumbnail and the picture opens full screen. The ⋮ in the corner there is the way back out of the app with it — for a long time there was none, and a photograph put into a record was a photograph that could not leave it.

  • Share — the phone's own share sheet: a message, mail, another app.
  • Save to Device — saves it where you choose, and a .jpg lands in the gallery's own listing rather than among files nothing knows what to do with.
  • Send to a server — the same two questions every upload asks, which server and which folder, and the same progress bar.
All three work the same on a MySQL record, where the picture is on the server: it is fetched first, used, and the fetched copy is tidied away afterwards. Your own photograph on the phone is never moved or renamed — only copied.

Filling a field without typing

Two readers are offered on every box you can type in — when you edit a cell, and in the add-a-record dialog, where several fields are filled at once. Each offers the camera or a picture already on the phone, the same two words the record's photos use.

  • Scan a code. A QR square, an EAN or UPC barcode, Code 128 — whatever the scanner recognises — and the value it holds goes into the box. It is offered on every field, not just one called something in particular: a code is an ordinary value once it has been read, and copying one off a label by hand is the thing worth avoiding.
  • Read text off a photograph. Point it at a label and the app lists the lines it found; pick the one you took the photograph for. All of it is the first row when you want the whole thing. A single line goes straight in without asking.
  • A picture already on the record is a third place to read from. The label is very often photographed into the record already, and going back to the camera to read it is photographing the same thing twice. That row is offered only on a record that has pictures — the add-a-record dialog has no record yet, so it does not.
A reading is added, never put in place of what is there. It goes in at the caret and on a line of its own, so a box holding Data and a scan of maliki comes back as the two of them, one per line, rather than as Datamaliki. Read into an empty box it is just the reading.
Camera or gallery is one sheet, and its rows can be dragged. Hold a row and move it: the one you reach for lands at the top and stays there. Each sheet keeps its own order, because they are different decisions — a code reader is answered with the camera almost every time, and "add a picture" almost never is.
Both read into the box, never into the row. Nothing is saved until you press Save, exactly as if you had typed it — so a code that scanned wrongly is one you can correct or throw away, and a QR square holding a few thousand characters cannot write itself into your table.

Codes drawn from a column

Beside those two there are two more, and they work the other way round: they take what is in the field and draw it.

  • Barcode — EAN-13 or EAN-8 when the value is one, Code 128 otherwise. A shelf label: a scanner at a till, a number read at arm's length.
  • QR code — holds far more and is read by any phone, which is what a link, an address or a whole line of text wants.

The app never guesses which you want: the same article number is a fair answer to both, and which one is wanted is a question about the table. From the picture either one shows you:

  • Show on card — pins the barcode under that column on every record of the table, so a shelf label or a serial number can be scanned straight off the screen. Tap it again on a record and it comes off. Kept on this phone, per table, and it follows a column rename and a table rename.
  • Add as image — attaches a PNG of the barcode to this record's photos, where it travels with the record like any other picture.
Show on card stores no picture. Flutter draws the code from the cell's text every time the row is drawn, so correcting the value corrects the code with it. One code under a column, not two — picking the other kind replaces it, because two stacked under one cell is a card nobody can read. Black on white whatever the theme — a scanner does not read a dark mode. A value nothing can be encoded from says so rather than drawing something a scanner would refuse.
Every QR is drawn with 15% error correction, not the 7% that would fit more in. These end up on labels in corridors, where a code is scuffed and rubbed at for years — and 2331 bytes is far more room than one record needs. One whole record of a real printer table measured 154 bytes, so fifteen of them would still fit in one square.
The cell editor is a list of rows, not a strip of icons. Scan a code, Read text, Barcode, QR code — each with its name beside it, and Cancel and Save at the foot where every other dialog puts them. The two that read into the box come first and the two that draw from it after, which is the order a value moves. The add-a-record dialog has a field per column and often a dozen of them, so it carries two icons under its title instead — Scan a code and Read text, acting on the field you are typing in. Only the two that read something in: a barcode is drawn from a value, and in that dialog there is no value yet. Its boxes grow with what is typed into them, up from one line, so a description of three lines is three lines you can see — and a reading off a photograph, which arrives as several, is not hidden in a box one line tall.

Columns the app fills in for you

  • A column with a fixed list of values is picked from, never typed into. If a MySQL column is declared as an enum, the app shows you its values to choose from. This matters more than it looks: MySQL outside strict mode does not reject a value the list does not have — it silently stores an empty string, and the cell you just filled in comes back blank with nothing saying why.
  • A column the database maintains is shown but not editable. Any MySQL column set to update its own timestamp, and any column called updated_at, is drawn greyed out and left out of the add-a-record dialog. Anything you typed there would be overwritten on the next edit anyway.

Search & sort

  • The list comes back in the order you set with Sort by on the database's own menu (see section 2) — newest first, where that is a date. With nothing set, the rows still come back in a settled order, so paging never shows you one record twice and hides another.
  • Search with filters: contains, equals, greater/less than, and between.
  • Sort ascending or descending by any column.
  • A search can also be written as SQL — the condition and the ordering are taken from what you type and applied to the list, which keeps its own paging and images.
  • Search results can be exported straight to CSV.

Column management

Columns can be added, renamed, deleted, retyped and reordered at any time, without leaving this screen. Each row carries an eye, which is what the card shows and not what may be done to it, and the last row of the list — Camera and delete — is the two buttons the card draws in its corners. See What a card shows above.

Column types

The type dropdown offers five, and which five depends on the table:

Ordinary tableSTRICT tableHolds
TEXTTEXTText. The default.
INTEGERINTEGERWhole numbers.
REALREALNumbers with decimals.
BLOBBLOBBinary data, stored exactly as given.
NUMERIC—A number where the value converts, text where it does not.
—ANYAnything, kept as it was given.

A STRICT table trades NUMERIC for ANY and then enforces the column's type on every write. That is SQLite's own rule rather than the app's. The dropdown switches by itself once a table is STRICT, and turning STRICT on names any column whose type is not allowed rather than failing with a raw database error.

There is no date type. SQLite has none — and it silently accepts any word you write as a type, so DATE is stored as plain text just as BANANA would be. Keep dates in a TEXT column in ISO order (2026-08-27, 2026-08-27 14:30:00) so that sorting and comparing work, or in an INTEGER column as a Unix timestamp. On a MySQL connection it is different: there DATE and DATETIME are real types.

Changing an existing column's type rebuilds the table and copies the values across without a CAST, so what fits is converted and what does not is left alone — 'abc' stays 'abc' rather than turning into 0. The app then tells you how many values did not take the new type. The primary key cannot be retyped: it carries AUTOINCREMENT, which only survives on INTEGER.

5. SQL Query

The SQL console, reachable from the tool row on any screen or from the SQL button inside a database. It has syntax highlighting and takes any statement: 

SELECT, INSERT, UPDATE, DELETE, CREATE TABLE, ALTER TABLE, ...

Results of a SELECT are shown as a paged table, and can be exported.

Two pickers in the title bar

  • The database picker switches which database the console is pointed at — local files and saved MySQL connections alike, listed in the same order as the main screen.
  • The table picker next to it rewrites the query box to SELECT * FROM `table`; for the table you choose, which is the quickest way to start looking at something.

Your query is kept

A half-written query is not lost when you step away to the Web View or the editor and come back. The text stays in the box until you clear it, saved per database — and per table when the screen was opened on one — so two tables never hand each other the wrong query.

The SQL Query button on the tool row also remembers which database you were last working on and returns you to it. The SQL button inside a database deliberately does not: it opens on its own database and leaves the remembered one alone, so a detour never moves where the tool row comes back to.

6. MySQL Connections

Add a remote MySQL server from the + button on the main screen. Once added, a MySQL connection is browsed exactly like a local database — same tables screen, same records screen, same SQL console — except every statement runs on the remote server.

The fields

The form is in two named groups, because it does two different jobs. MySQL is everything used to dial the database. Pictures is everything reached over HTTP instead — the PHP image API, the folder the photographs sit in, the two published pages, and the server all of that is uploaded through. The connection's name is above both, because it belongs to neither: it never reaches a server.

Times read the same wherever your server is. Nothing already stored is changed — MySQL keeps a TIMESTAMP in UTC and converts it on the way in and out. Note that only TIMESTAMP works this way; a DATETIME column is never converted by anything.
A dropped connection is redialled. Shared hosts hang up on an idle connection within minutes, which used to break a long export halfway through. Now the app simply dials again and repeats the read. Only reads — an insert that reached the server but lost its reply is never sent twice.

Use SSL — and what it changes

With Image API host empty, the Use SSL switch does two things at once. It makes the MySQL connection itself encrypted, and it decides the scheme used to reach the image API: 

Use SSL ON   →  https://name.duckdns.org/my_database_api.php
Use SSL OFF  →  http://name.duckdns.org/my_database_api.php

The line under Image API host shows that exact URL as you type, so there is never any doubt about what the app will call. This is also why Server IP/Host takes a bare address: the scheme is the switch's job, and a host typed as https://myserver.org produces https://https://... — which the preview shows you immediately.

Fill Image API host when the PHP file is not on the MySQL machine — Cloud SQL has no PHP, and a shared host's MySQL hostname is not the website. That same preview then follows this value instead: 

https://example.com           →  https://example.com/my_database_api.php
https://example.com/my_database_api.php  →  used as typed
192.168.1.115                 →  http://192.168.1.115/my_database_api.php

A value that already has a scheme, or that already ends in .php, is used as typed. A bare address is reached over HTTP: the SSL switch is then only for MySQL's TLS, because a second host is almost always an IP without a certificate.

If the server sends HTTP on to HTTPS, pictures still show but adding, deleting or reordering them fails. The app then says The image server only answers over https and names the address to use — type it into Image API host with https:// in front.

If the PHP file sits on the MySQL host and that server only serves HTTPS, images will not work with Use SSL off. A certificate is issued for a name, not for an IP address, which is why a hostname is the better thing to put in Server host for a public server that also serves the API.

Certificates

With Use SSL on, three optional fields appear: CA certificate, client certificate and client key, each in PEM form. A folder button beside each one picks the file from the phone. Leave them empty for an ordinary public certificate; fill them in when your server expects a private CA or client authentication.

Images on MySQL

A local database keeps its images in a folder on the phone. A MySQL database cannot — so image folders live on your web server and are managed through my_database_api.php, using the API key from the connection dialog. Creating, renaming and duplicating a table keeps its image folder in step. Dropping one does not delete its pictures on the server — a photograph is the one thing no restore can invent, and the folder is yours to clear out when you mean to (Files on a server, the terminal, or your host's file manager). On the phone, where the folder is inside the app's own storage and nothing else can reach it, dropping a table does take its pictures with it. If the API key is missing, the app says so on entry: the database still works, but image features will not.

Step 3 — Name

The file name is checked before anything is written. Characters that cause trouble on Android, on Windows or in a remote path are replaced with _; database exports are stricter still, because the name also ends up in the PHP viewer's URL. A name that is already taken is the system dialog's business — it numbers the new one — so the app no longer asks you about overwriting anything.

There is no size limit on an export. Everything is written and read a buffer at a time rather than held in memory, so a database with a few hundred megabytes of photographs saves exactly like a small one.

Import from...

  • A ZIP previously created by the app (database + images).
  • A plain .db SQLite file.
  • A CSV file — a new table is created from its header row. You are asked which delimiter the file uses, so semicolon-separated exports from European spreadsheets import correctly.
A name already on the phone is asked about. Import a MyDb while you already have one and you are offered Replace or Keep both — kept, the incoming one lands as MyDb_1 and yours is untouched. Nothing is ever merged into an existing database: the two sets of images would end up in one folder, beside a database that knows nothing about half of them.
MySQL connections can be exported too, but have no "Publish as web page" option — a database that already lives on a server has no reason to be uploaded back to itself.

8. Backup & Restore

An export copies one database. A backup copies them all, in one action, into a single file — which is the one worth having before a new phone, a reinstall, or anything that makes you hesitate. Both rows are in Setup.

Back up everything

One zip, holding four things:

  • Every local database — the .db file, its write-ahead log, and the images beside it, folder for folder.
  • That database's settings — which columns the record list shows (and whether the card's two corners are drawn), which column each table is sorted by, how the record list is drawn, and any barcode pinned under a column.
  • Your saved logins, as connections.json: MySQL connections, the named SFTP/FTP servers, the SSH terminal connections, and one API key per AI provider.
  • Your saved pages and your list order — the Web View's bookmarks, and the order you dragged the database list and each database's tables into.
  • Your terminal hints, when you have edited them.
  • It goes wherever an export can — Save to Device, Share, or an upload to a saved server.
  • The name it suggests puts the date first — 2026-09-12_MDbackup.zip. A file list cuts off the end of a name, and the end is where the date used to be, so every backup on the phone read as the same word. Turned round it survives being cut, and sorting by name is sorting by date.
  • It never asks for a password. A locked database is copied as the encrypted file it is, and comes back needing the same password it needed before.
  • There is no size limit. The file is written a buffer at a time rather than assembled in memory, so a phone full of photographs backs up like any other.
The zip itself is the secret. Your logins are written into it in the clear, and that is deliberate: the stored form is encrypted under a key that cannot leave this phone, so a copy of it would open on no other device — written out plainly, it actually restores. Treat the file the way you would treat a sheet of paper with your passwords on it. Two things are deliberately left out: your database passwords, because a backup that could open its own encrypted files would not be worth much, and the Puter token, which is fetched again from the API key that is in the zip.
A backup password seals the logins. Setup → Backup password. Once it is set, Back up everything asks for it before anything else, and the logins and the terminal hints go into the zip encrypted with it (AES-256) — unzipped, they are unreadable. The databases and pictures stay ordinary files. A restore asks for the same password; press Cancel there and everything comes back except the logins. Somebody you lend the phone to therefore cannot send themselves your passwords through a backup. Forget the password, and the logins in that backup are lost — the rest is not.

Restore from a backup

  • It first asks where the backup is: this phone, or a server — in which case it browses a saved server and fetches the zip for you. Everything after that is the same either way.
  • Then it asks which of two restores — every time, before anything is written.

Add to this phone

  • Nothing here is removed. A database whose name is also in the backup is kept beside the one here, as name_1, with its settings and its place in the list following it.
  • Logins and saved pages merge. A login is matched by name and a page by its address, so a page you renamed on one phone is still the same page. Anything already here is updated, anything new is added, anything the backup does not mention is left alone — and a restored page keeps its place rather than jumping to the end.
  • The order on your screen wins; anything the backup knows about that you do not is appended.

Replace everything

This phone becomes the backup. Use it to make a second phone match the first — which is what it is for, and what merging could never do: restoring a four-server backup onto a phone that had its own servers used to leave you with seven.

  • Every local database here is deleted and the backup's put in their place. The logins, servers, saved pages, list order and pairings are written over what is here rather than merged into it.
  • Anything not in the backup is gone for good — databases included. The confirmation tells you how many databases are here and how many are in the backup before you choose.
  • A section the backup does not carry at all is still left alone. An older zip simply has no such part, and "match the backup" cannot sensibly mean "delete the things this backup was written before".
Neither choice ever merges into a database that is already here. Your rows are never mixed with a backup's.

9. Publish to Web (PHP Viewer)

One of the app's signature features: turning any database into a real website with a single tap, no web-development knowledge needed.

  • Publish as web page (or the "PHP viewer" export) creates two ready-made PHP pages named after the database, sitting next to the .db file on your web server: MyDb.php and MyDbai.php.
  • MyDb.php is the plain reader — the whole database as cards with photos, a search box, and Print / Save as PDF. It holds no API keys, so it is the one to share.
  • MyDbai.php is the same page plus the AI search and the SQL box. It is the only one that uses AI keys, and it ships with them empty. To use OpenRouter, Mistral or Claude, open MyDbai.php on your server and paste your key between the quotes at the top: 
    $openrouterApiKey = 'sk-or-v1-...';
$mistralApiKey    = '...';
$claudeApiKey     = 'sk-ant-api03-...';
    Publishing the page again from the app writes the empty copy back, so paste the key again after that. Ollama needs no key. Without a key the AI box simply says none is set. The SQL box on this page runs one read-only statement at a time and nothing else, whatever it is dressed up as.
  • Each table is listed in the order you chose with Sort by in the app. The choice goes up beside the database as MyDb_sort.json. With no choice, or a column that no longer exists, the page shows the rows as they are stored.
  • A page for a MySQL database keeps itself up to date. When you change something on the server through the app — a record, a table, a statement in SQL Query — the app sends the page a fresh copy of the database a few seconds after you stop, and does the same after you leave Sort by. It only does this where the page already is: the connection's paired server, in its Image folder. Changes made outside the app (phpMyAdmin, another phone) are not seen until the next change made in the app.
  • The AI search box in MyDbai.php searches only that one database — MyDbai.php learns MyDb, Animalsai.php learns Animals — and does not answer general questions. A code or name is turned into SQL on the page; longer questions go to a locally hosted Ollama model (free) or a cloud API. The provider and your own API key are configured by editing a few lines near the top of the generated PHP file — the same rule as in the app: the key is yours, not the app's.
  • A single switch inside that file, $editing = 'on' or 'off', controls whether visitors are allowed to edit data or only view it.
  • A password-protected database still works. The page opens its database with plain SQLite and no key, so the upload publishes a decrypted copy — made through the database you already have open, so nothing asks you for the password again. The copy on your phone stays encrypted. Only Publish as web page does this; an export of the database itself, and the ZIP you can import back, keep their encryption.
  • The upload also puts an .htaccess beside the page, so a browser cannot download the .db or the .sql directly. The page is meant to be read over the web; the data behind it is not.
Because it is a plain PHP file, the published page can be opened, inspected and customised in this app's own Code Editor — and actually run through the PHP Preview — before it is ever uploaded.

10. Servers — SFTP & FTP

A list of named servers, not one slot. Setup → Servers opens that list. Add as many as you have hosts — a home Mac Mini, a VPS, a shared-hosting account — each with its own name, address and folders.

A server speaks SFTP or plain FTP, and you say which. Most shared web hosting offers FTP on port 21 and no SSH at all, so a host like that can be set up and used exactly like an SFTP one. One thing genuinely differs: over FTP a file counts as changed by its size alone, because there is no dependable way to stamp a date onto what was just uploaded. Over SFTP the app sets the date itself and compares both.

One server, both protocols

A machine you can reach two ways is one entry, not two. The Protocol switch chooses which way is in use, and everything except the name is remembered separately for each — address, username, password, port, and both folders. Flip the switch and the other set comes back exactly as you left it.

That matters because the two are rarely alike:

  • Hostinger answers FTP on 21 and SFTP on 65002 under different passwords, and its folders are absolute over the one and relative over the other, because SSH lands in your account home.
  • A Mac Mini is 192.168.1.115 over FTP on your own network and a DuckDNS name over SFTP from outside it — the same machine at two addresses.

Filling in a protocol you have not used yet starts from the address and account already on screen, since most servers answer both in one place; usually only the port and the password need changing.

The switch is a setting, not a question during an export. An upload uses whichever protocol the server is set to right now; to send over the other one, come back here and flip it. There is deliberately no automatic fallback — quietly dropping from SFTP to plaintext FTP is not a decision the app should make for you.

Test connection

On the same form, and worth using before your first upload. It dials, logs in and looks at both folders — using the fields as they stand, not as they were last saved.

  • It always gives you an answer. A folder that does not exist yet is reported, not treated as a failure, because an upload creates what it needs.
  • That report is the point. A mistyped /https/maps/ is created just as happily as /htdocs/maps/ — and afterwards nothing tells you your files went somewhere nobody will ever look.
  • If it cannot connect, the message names the host and the port the app dialled. The raw network error names a local port instead, a number you never typed, which is no help at all.

Which server an upload goes to

A local database and a MySQL connection can each be paired with a server. A connection's pairing you choose, on SFTP server in its form. A local database's you do not: it is written down the first time an upload has to ask you which server to use, and the only place it can be seen afterwards is the Used by line under each server in Setup → Servers. Either way, which server an upload actually uses is asked during the export, right after you choose the destination — so the folder shown in the later steps is the folder your file really lands in.

  • The paired server is ticked, not forced, and picking a different one this time does not change the pairing.
  • The question is skipped when there is nothing to choose: one saved server is not a menu, and none opens the setup form.
  • When the upload finishes, the app tells you the full path the file landed at and names any folder it had to create to get there.

A folder upload is a sync, not a blind re-upload: the app scans what is already on the server, sends what changed, skips what did not, and removes files that no longer exist locally. When it finishes it reports how many files were uploaded, skipped, deleted and — if any — failed, so a partial upload is never mistaken for a complete one.

A folder path is always treated as a folder. If you type it without the trailing slash the app adds one, so an upload cannot end up writing a file alongside the folder instead of into it.

Files on a server — Setup

Shows what is actually on a server, and is how you put anything from your phone there — a photo, a PDF, a whole folder. Nothing else here does: every other feature writes into folders it was told about and never reads one back, so a file that landed in the wrong place stayed invisible until a page failed to change.

  • List folders, upload, download, rename, delete a file, delete an empty folder, make a folder. Deleting a folder is not recursive, and a server that refuses tells you so.
  • Upload asks one thing — Files (one or several) or A folder (everything in it, subfolders and all) — and puts it in the folder you are looking at. A folder lands in one of its own name: sending Camera while you are in /htdocs/ puts it in /htdocs/Camera/. It all goes on the connection the screen already has, each file fetched only when its turn comes, and a file the phone will not hand over is passed over and counted rather than losing the rest.
  • You can also start from another app. Share a file to My Database Pro from the Gallery or Files and the app asks which server and which folder, with that file in hand.
  • Rename is the one thing here that changes a server without destroying or sending anything — a file uploaded under the wrong name used to mean downloading it, deleting it and sending it back up. It works on a folder too. A name already in the listing is refused, and so is a name with a slash in it: that is a move, not a rename.
  • Uploading over a name that is already there asks first. Neither protocol asks — both overwrite in silence.
  • Hold a row to see where the file really is, and it is copied at the same time — Copy path is on the row menu too. This screen is the only thing that knows: a row carries a name, and the path is that name under whichever folder you have walked into. Use it before typing a path into the Terminal, or before asking the AI about a file. Folders have a path too, ending in a slash — and the path is shown on screen whether or not the clipboard accepted it.
  • Look at a picture without leaving the app — View image on the row menu. A text file can be opened in the editor and saved straight back to the server.
  • Double-tap a file and it does whichever of those two fits: a picture opens in the viewer, a text file in the editor. Both stay on the menu as well, since nothing on a row tells you it can be tapped twice. Download stays on the menu only — it asks where to put the file, and a gesture should not start a conversation.
  • Back goes up one folder, not off the screen. Only when there is nowhere left to go back to does it close the browser.
  • It opens on the server's Remote Directory rather than the root — on shared hosting the root is full of folders you did not make and cannot write to.
  • The browser is also a picker. It is how you choose the folder an upload goes to, and how you find a backup on a server to restore from. In those modes the folders still open, but everything that changes the server — upload, delete, new folder — comes off: a picker is not a place to delete things.

11. Code Editor & PHP Interpreter

A multi-tab code editor with syntax highlighting. Open and save files on the phone, undo/redo, and find and replace within a file.

  • HTML files get a live Preview.
  • PHP files get a real Preview: the app ships an actual PHP 8.5 interpreter, with the mysqli and pdo_mysql extensions built in, and runs the file on a small local server on the phone. PHP scripts that connect to a remote MySQL server can be written and tested without leaving the app. (Android only.)
  • Leaving the editor asks nothing and loses nothing: every tab, unsaved text included, is kept and is there again next time. Closing a tab with unsaved changes asks first. Tabs with unsaved changes are marked.
  • Files that are not text are refused rather than opened, since opening one here would corrupt it — and the next Save would write the damage back over your original.
  • A tab remembers where you had scrolled to; a newly opened one starts at the top.

Working on files that live on a server

A .php on a web host is a file to edit, not one to download, change, and upload again by hand.

  • Open from server in the editor's menu — or Open in editor while browsing a server — opens the file straight off the host.
  • Save writes it back to where it came from. The tab remembers which server, but never the password, so a server you deleted in the meantime gives you a message rather than a crash.
  • Opening the same file twice takes you back to the tab already holding it, instead of making a second copy that could overwrite your work.
  • Upload to server is a third answer to "where does this go", beside Save and Save as. It writes a copy somewhere the tab has no relationship with: your tab keeps its own file and stays unsaved if it was. A file that quietly started saving somewhere else would be the worst kind of surprise.

Editor settings

The editor has its own settings, separate from the app's:

  • Text — font size, line height, tab size, word wrap, line numbers.
  • Appearance — the syntax colour theme.
  • Reminder — whether a date and weekday separator is inserted into reminder.txt at startup.
  • Auto-opened files — which bundled files open as tabs when the editor starts.

The reminder note

Every time the editor opens, a tab called reminder.txt is ready and waiting — a persistent scratchpad that autosaves to the phone as you type, so it is always there for quick notes.

13. SSH Terminal

A full terminal (built on xterm) to any server you manage over SSH. Connections are saved by name, host, port, username and password.

The Terminal button on the tool row reconnects straight to the connection you last used, rather than making you pick it out of the list again; Back still reaches the list underneath. An SSH session cannot truly be resumed — leaving the screen drops the connection — so this reconnects rather than restores.

The server's host key is remembered the first time you reach it, and every connection after that has to present the same one — the same thing an ssh client does with a host it has never met. It is what makes the password you type go to the machine you meant. If a server is genuinely rebuilt its key really does change, and the app will refuse it; deleting the saved connection or server forgets the old key along with everything else kept under its name, and the next connection writes down the new one. The same check covers Files on a server and every upload.

Output text can be selected with on-screen handles for copying, just like in a desktop terminal.

Hints

The light bulb in the title bar opens your hints: commands you use often, one tap from the prompt. They open as a panel under the key bar, the way the keyboard does, so the terminal shrinks above it and the prompt stays in sight. A tap pastes the command into the prompt and never runs it — press OK to send it. The panel stays open for the next one; close it with ✕ or the bulb.

The hints are one text file, edited whole with the pencil in the panel. A line starting with ### names a hint, and the lines under it are its command: 

###Create database Animals
mysql -u root -e "CREATE DATABASE Animals;"

###Import a .sql file from the phone into Animals
mysql -u root Animals < {file}

Save keeps your copy; Reset to default in the menu goes back to the hints the app ships with.

{file} in a command asks for a file. Tapping the hint asks where it is — this phone or a server, the same two answers a restore asks for — sends it to your home folder on the server over the connection you are already on, and pastes the command with {file} replaced by where it landed — for example mysql -u root Animals < ~/Animals.sql — waiting for OK. A file of the same name already there is replaced.

Or the app can write one for you. The third answer is Make one now: pick one of the databases on the phone and the app writes a fresh .sql of it, sends it up and fills the command in — no export, no Save to device, no hunting through Downloads. It is also the only one of the three that is guaranteed current; a dump sitting on a server is whatever the last export left there. Local databases only: dumping a server's database to feed it back into a shell on that same server is not a thing anybody wants.
And it does not ask which database when your command says. A hint reading mysql -u root MyDb < {file} is a hint about MyDb, so Make one now writes MyDb.sql and pastes it — no list to pick from, and no way to send the wrong database to a command naming another. It only does this when your command names exactly one of your databases: naming two, or naming one by accident (a database called root, in mysql -u root MyDb), brings the list back, because then the app has no right answer.
A server is offered because that is often where the file is. A .sql written by an export is as likely to be sitting on a web host as on the phone, and fetching it with something else just to pick it out of Downloads was the way round that. A file taken off a server is still sent up to the home folder rather than named where it lies: there is no telling from the terminal whether that server is this machine — a host answers to several names, and through two different logins — so the app never guesses.
Several lines pasted at once all go to the shell, not into a program the first line starts: mysql -u root followed by a CREATE line does not run the CREATE inside MySQL. Give MySQL the statement on the same line with -e "…".

16. Security & Your Data

  • Database passwords. Setting a password on a database encrypts the whole file, not just the screen in front of it. Without the password the file is unreadable, in the app or out of it.
  • Saved credentials. SFTP details, MySQL and SSH connections and AI API keys are stored encrypted. On Android the key lives in the hardware-backed Keystore; on Windows the platform's DPAPI is used. The key never leaves the device.
  • What that means for backups. Because the key cannot leave the device, copying the encrypted values into a backup would only carry over a blob nothing could read. So the backup writes those logins out in the clear instead, which is what makes them actually come back on a new phone — and what makes the backup file itself worth protecting. See Backup & Restore.
  • A saved login can be locked, and it is one password for all of them. On a MySQL row it is Add Password under Connection Options; on an SFTP-FTP server and on an SSH connection it is in that entry's own form. The first lock sets the password — every one after it asks nothing, because there is only ever one key. Take the last lock off and the key is thrown away, so the next lock can ask you for a new one.
  • A lock stops the screen that shows the login, not the login. That is the whole point: the phone can be handed to somebody with the databases usable and the logins unreadable.
    • An SFTP-FTP server: its form will not open, and neither will Files on a server or the folder picker on it. An export or an upload to it asks for its password first, as soon as the server is chosen — Copy to MySQL server too. A server with no password is not asked about.
    • A MySQL connection: Edit Connection, re-pairing and Delete will not open. Opening the database, reading it and exporting it all still work.
    • An SSH connection: the form, the session itself, and Delete. Stricter on purpose — a shell on your server is the thing itself, not a form about it.
    • Delete asks for the key on all of them, and for a local database it asks for that database's own password. A lock that guards the sight of a login while the whole thing can be thrown away is not much of a lock. Rename and duplicate stay open: both leave the original where it is.
    A connection paired with a locked server is locked too, and its row shows the padlock — the lock belongs to the server, so it comes off where it went on.
  • What the lock is not. It is not encryption, and it is not a lock against somebody with your phone and a computer. The credentials are exactly as readable to the platform as they were before, and the app's own backup carries them in the clear on purpose. It is a lock against the person you handed the phone to, and it is worth saying that plainly. The locks travel in a backup so a restore does not quietly take them off — but this phone's key always wins, and the backup's locks are added to it rather than replacing it.
  • Your database passwords are the exception. They are never written into a backup in any form. After a restore or a reinstall an encrypted database still asks for its password, and nothing in the app can recover it for you. Keep it somewhere you trust.
  • A backup keeps the lock on. A password-protected database goes into a backup as the encrypted file it is, so the backup is safe to leave somewhere else and needs the same password wherever it lands.
  • Everything is yours. The databases sit on your phone, exports go where you send them, and the only servers the app talks to are the ones you configure yourself.
Keep your own backups of anything important. Setup → Back up everything takes the lot in one file; a ZIP export of one database before a risky change takes seconds and includes its images.

  • Use the reminder note in the Code Editor as a running journal: it autosaves as you type, so nothing is lost even if the app closes.
  • Before making risky changes to an important database, export a ZIP backup first — it takes seconds and includes your images.
  • If you are unsure what a column or table is called, let the AI assistant write the query — it always uses the exact real names from your database.
  • Add the SFTP servers in Setup first, then pick one on the database (or on the MySQL connection). Every export after that is a couple of taps, and a folder upload only sends what actually changed.
  • For a public MySQL server that also serves the image API, use a hostname rather than an IP and leave Use SSL on — the certificate is issued for a name. If MySQL and PHP are on different hosts, put the website in Image API host and leave Server host as the database hostname.

18. Server Setup for Pictures (my_database_api.php)

What it is

Pictures on a MySQL database cannot live in MySQL, so they are kept as files on your web server, in a folder called my_database_images. The app reaches them through one PHP file, my_database_api.php. Rows and tables work without it; only pictures need it.

My Database and My Database Pro use the same file, so a server set up for one works with the other.

1. Download and upload the file

  • Download my_database_api.php (or as a .zip). It is also in the GitHub repository.
  • Upload it to your web server's public folder (for example public_html/, htdocs/ or /var/www/html/).
  • The server needs PHP 7.1 or newer. Apache, LiteSpeed and nginx all work.

2. The pictures folder

  • The file keeps pictures in my_database_images/ next to itself, as {database}/{table}/{record id}/.
  • It creates the folder on the first upload if PHP may write to the web folder. If it may not, create my_database_images yourself and make it writable by PHP (on most shared hosting it already is; otherwise chmod 775).

3. Set your API key

The file ships with no key and refuses every request until you add one. Open it and find:

$API_KEYS = [
    // 'put-a-long-random-string-here' => 'admin',
];

Add a line with your own key and a role:

$API_KEYS = [
    'c3f9a1e07b5d42e8a6f0b91d7c2e4a58f1b6d9e3' => 'admin',
];
  • A key must be at least 16 characters; a shorter one is refused. Use a long random string, not a word. php -r "echo bin2hex(random_bytes(24));" makes one, or use a password manager.
  • Type the same key into the app, in the MySQL connection's Server API Key field.
  • You can add more than one key, one per person or phone, each with its own role:
    • admin: everything.
    • uploader: see, add and reorder pictures, and delete only the pictures it added itself.
    • viewer: see pictures only.

4. Use HTTPS

  • Give the server a certificate (Let's Encrypt is free). The key travels with every request, and over plain HTTP anyone on the way can read it.
  • A certificate is issued for a name, not an IP address, so reach the server by its name.

5. Test it

The app sends the key in an X-Api-Key header, never in the address, so a browser cannot test the file. From a computer:

curl -H "X-Api-Key: YOUR_KEY" "https://yourserver.com/my_database_api.php?action=list_images&db=test&table=test&post=1"
  • The answer should be {"success":true,"message":"","data":{"images":[]}}.
  • Invalid or missing API key means the key is missing from the file, shorter than 16 characters, or not the same as the one you sent.
  • Then, in the app, add a picture to a record on that connection.

What the file protects on its own

  • It accepts only picture files (JPEG, PNG, WebP, GIF, BMP, HEIC), checked by name and by content.
  • It writes an .htaccess into each table's folder so nothing there can run as a script, and keeps its own bookkeeping files from being downloaded. (nginx ignores .htaccess; the checks on every upload still apply.)
  • Anything that changes the server has to be a POST, so a link opened by a crawler or a link preview cannot delete pictures.

Upgrading from the older file

If your server runs the older my_database_api.php (the one with $API_KEY = '8888';):

  • Replace it with the new file and set a key in $API_KEYS as in step 3, at least 16 characters. 8888 no longer works.
  • Put the same key into each MySQL connection in the app.
  • Pictures already on the server stay where they are. Nothing needs moving.
  • The new file needs My Database 1.2.8 or newer, or any version of My Database Pro. Version 1.2.7 and older send the key in the address, which the new file does not accept, so they show no pictures until the app is updated.
